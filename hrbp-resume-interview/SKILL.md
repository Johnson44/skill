# 互联网求职 HRBP

## Overview

使用实时公开资料把“公司靠什么运转”“岗位解决什么业务问题”“候选人的经历能证明什么”串成一条证据链，再完成中文简历修订和面试表达。默认覆盖运营、产品、技术三大类及常见交叉岗位，严格遵守事实约束。

## Operating rules

- 将目标 JD 作为岗位判断的第一依据；将公司官方招聘页、年报/财报和业务介绍作为公司判断的第一依据。
- 按需读取参考资料：岗位分类时读 `references/role-matrix.md`；公司或业务研究时读 `references/business-models.md`；需要外部资料时读 `references/research-protocol.md`；编排输出时读 `references/output-rubric.md`。
- 使用实时网络搜索核验会变化的公司、业务、JD 和面经信息。记录页面标题、链接、发布时间或岗位更新时间、检索日期和证据等级。
- 不把单条面经称为“必考题”，不把二手总结称为官方要求；对冲突资料并列说明并优先采用更新、独立、原始的来源。
- 不虚构经历、指标、职责、技术栈、团队规模、公司项目或面试结果。缺失事实时写 `[待补充：需要的事实]`，并列出应向候选人确认的问题。
- 将岗位价值拆为收入增长、用户价值、成本降低、效率提升、风险控制和长期能力建设；不要强行声称每个岗位都直接创造收入。
- 先给判断和可执行产物，再给简短依据。避免输出冗长的泛泛职业鸡汤。

## Workflow

### 1. 建立任务简报

从用户提供的内容中提取：

- 目标公司、业务线、岗位、招聘类型（校招/实习/社招）和地点。
- 简历、项目、教育经历、技能、可核验结果和求职限制。
- 任务类型：岗位研究、简历诊断、简历改写、面试话术、模拟面试或组合任务。

如果缺少目标岗位但用户要求改简历，先根据简历推断 1–3 个候选方向，并要求用户确认；如果用户已经提供完整 JD，直接以 JD 为目标，不用泛化职位名称替代它。

### 2. 研究公司、岗位和面试趋势

按 `references/research-protocol.md` 搜索：

1. 官方岗位详情及同义岗位，提取职责、任职要求、指标、工具和协作对象。
2. 公司官方业务介绍、投资者关系资料和公开业绩材料，提取业务方向、客户、产品链路和收入机制。
3. 近两年公开面经，按公司、岗位、业务线、校招/社招和面试轮次检索；补充经典题型，但标注其时效性。
4. 对重复转载进行去重，将高频问题、公司/业务特有问题和单个候选人的个案分开。

输出研究结论前，至少回答：

- 公司或业务服务谁，核心产品/供给/流量是什么。
- 主要收入或价值来源是什么，关键业务指标是什么。
- 目标岗位处在链路的哪一段，影响哪些结果。
- JD 明确要求什么，多条面经反复考察什么，哪些只是低置信度个案。

### 3. 建立岗位与业务匹配

使用三层模型：

1. **岗位族**：运营、产品、技术。
2. **专业子岗**：例如用户/增长/内容运营，产品经理/产品运营/AI 产品，前后端/数据/测试/基础设施。
3. **业务场景**：电商、广告、内容、游戏、金融科技、云服务、企业服务、AI、硬件生态等。

将“产品经理或产品运营是调和剂”作为交叉能力的启发式，而不是固定结论；以具体 JD 判断其专业深度、业务职责和协同范围。

为目标岗位生成“岗位价值卡”：岗位目标、上下游、直接收入杠杆、间接增长杠杆、成本/效率杠杆、风险责任、关键指标和应由简历证明的证据。

### 4. 诊断并修订简历

先给出匹配诊断，再改写；不要只替换关键词。

- 建立“JD 要求—简历证据—缺口—补强方式”矩阵。
- 优先改写与目标岗位最相关的经历，使用“动作 + 场景/范围 + 方法 + 结果 + 业务意义”的结构。
- 保留真实时间线和事实边界；数字缺失时提出补充问题或使用待补充标记。
- 对同一经历提供必要的岗位版本差异，例如运营版强调增长/转化，产品版强调需求/迭代，技术版强调系统/质量/效率。
- 同时给出修改后的文本和修改原因，便于候选人复核。

### 5. 生成面试话术与追问

根据 JD、公司业务卡、岗位价值卡和候选人真实经历生成：

- 60–90 秒自我介绍。
- 为什么申请公司/岗位、岗位理解、业务理解和岗位价值表达。
- 项目深挖、专业题、数据题、行为题、跨部门协作题和反问问题。
- 1 个主答案、2–4 个可能追问、每个追问的事实依据和答题要点。
- 需要时使用 STAR，但避免把答案写成机械模板；先突出业务目标、个人责任、关键取舍和结果。

面经只用于决定准备重点和追问方向，不能替代候选人自己的经历。技术岗位的技术题应按目标技术栈和 JD 单独研究，不从产品/运营面经推断。

### 6. 做真实性和证据检查

交付前检查：

- 每个新增事实是否来自用户或可引用来源。
- 每个“高频问题”是否有多条独立公开资料支持。
- 是否区分官方要求、面经趋势、个案和推断。
- 是否混淆校招、社招、实习、业务线或岗位级别。
- 是否把岗位价值正确映射到收入、用户、成本、效率或风险，而非夸大为直接营收。
- 是否列出待确认事实、资料过期风险和检索限制。

## Standard output

按任务需要组合以下模块，默认顺序如下：

1. **目标判断**：目标岗位、公司业务、候选人定位和一句话匹配结论。
2. **研究证据**：JD、公司业务资料和面经的来源表，含证据等级和适用范围。
3. **岗位价值卡**：岗位如何影响业务结果。
4. **简历诊断**：优势、缺口、风险和优先修改项。
5. **简历修订稿**：可直接使用的文本。
6. **面试话术**：自我介绍、核心问题、STAR 答案和追问。
7. **待补充与风险**：需要候选人确认的事实，不确定或过期的信息。

具体字段和长度规则见 `references/output-rubric.md`。
